# SPHEREx AWS 数据管线：简明使用说明

更新日期：2026-09-21

这份文档用于解释：新程序和原来几个编号脚本有什么关系、当前 single-point
研究进行到了哪里，以及以后实际使用时应该关注哪些文件。

## 一句话理解这个项目

程序可以从 AWS 获取“文件清单”，从清单中选出需要的文件，然后安全地下载
FITS，并记录哪些文件已经成功下载。现在还增加了一个只读的 IRSA 位置查询，
可以先找出覆盖某个天空坐标的 SPHEREx images。

```text
给定 single point (RA, Dec)
          ↓
      IRSA query
          ↓
覆盖该点的 S3 keys ──────┐
                          ↓
AWS 文件清单 → 本地 catalog → manifest → 安全下载和检查 FITS
```

目前的空间查询只负责回答“哪些完整 FITS 覆盖这个位置”。项目仍不做光谱提取、
测光或其他科学分析。

## 和原来程序的关系

原来的学习过程是：

```text
01_list_spherex.py
        ↓
02_make_catalog.py
        ↓
03_parse_catalog.py
        ↓
04_download_test.py
        ↓
05_read_fits.py
```

这些脚本每个只做一件事，适合学习流程，但它们之间主要依靠手工操作：

- 路径写死在脚本里；
- 下载哪个文件需要修改代码；
- 只能通过“文件是否存在”判断是否下载过；
- 没有统一记录失败、更新和重试；
- 从不同目录启动脚本时可能找不到文件。

新程序没有改变原来的科学数据流程，只是把这些步骤组合成一个可以重复运行的工具：

| 原来的脚本 | 新程序中的对应部分 |
|---|---|
| `01_list_spherex.py` | `s3_access.py` |
| `02_make_catalog.py` | `catalog.py` 和 `database.py` |
| `03_parse_catalog.py` | `filenames.py` |
| 手工从 CSV 选择文件 | `selection.py` |
| `04_download_test.py` | `downloader.py` |
| `05_read_fits.py` | `verification.py` |
| 新增的天空位置查询 | `irsa.py` |

你不需要逐个运行这些新模块。它们统一由下面这个入口调用：

```bash
python -m spherex_pipeline
```

## 你日常真正需要关注的内容

### 1. `config.toml`

这是最重要的用户配置文件。

它决定：

- 查询哪个 S3 bucket 和 prefix；
- 测试选择多少个文件；
- 从哪个 planning period 选择；
- 下载到哪里；
- 同时下载几个文件；
- 是否验证 FITS 和计算 SHA-256。

当前配置是：

```toml
[selection]
planning_period = "2025W17_4B"
limit = 10
```

因此当前测试始终只选择 10 个 FITS。

### 2. `python -m spherex_pipeline`

这是唯一需要记住的程序入口。后面的单词表示要做哪一步。

目前可用的主要命令包括：

```text
catalog   更新或导出 AWS 元数据 catalog
search    查询覆盖一个 RA/Dec 的 SPHEREx QR2 images
select    建立普通下载 manifest
download  预览或执行 manifest 下载
verify    重新检查已下载文件
status    查看下载记录
```

### 3. `catalogs/spherex.sqlite3`

这是程序的工作记录本，里面保存：

- AWS 上有哪些对象；
- 对象是否新增或更新；
- 哪些文件已经下载；
- 下载是否成功；
- 文件大小、ETag 和 SHA-256；
- 失败原因和重试次数。

不要用文本编辑器或 Excel 修改这个文件。平时也不需要直接打开它。

### 4. `catalogs/test10_manifest.csv`

这是已经选定的 10 个测试文件清单。

manifest 的意义是把本次选择固定下来。以后反复 debug 时，程序仍然使用同一批文件，而不是每次随机换 10 个。

可以用 Excel 或文本编辑器查看，但暂时不要手工修改。需要重新选择时，应运行 `select --overwrite`。

### 5. `data/qr2/...`

这里保存真正下载的 FITS 数据。

目录结构和 S3 key 保持一致，例如：

```text
data/
└── qr2/
    └── level2/
        └── 2025W17_4B/
            └── l2b-v20-2025-240/
                └── 2/
                    └── level2_....fits
```

以后迁移到 HPC 时，主要需要迁移或重新配置的就是这个数据目录。

## 最简单的日常操作

首先进入环境和项目目录：

```bash
conda activate spherex
cd /mnt/c/Users/26823/Desktop/SPHEREx_project
```

### 查询覆盖一个天空位置的 images

输入 ICRS 十进制度数，例如：

```bash
python -m spherex_pipeline search \
  --ra 210.80225 \
  --dec 54.34894
```

该命令会向 IRSA SIA v2 服务发送只读查询，输出：

- 覆盖该位置的 QR2 Level 2 FITS；
- 每个结果的 detector；
- 完整 AWS bucket 和 S3 key；
- 每个文件以及全部结果的预计体积。

程序实际使用一个半径为 0.036 arcsec 的小圆作为 single-point probe，约为
SPHEREx 一个像素的 1/170。它不会下载 FITS，也不会自动创建 manifest。

IRSA 偶尔可能返回 `502 Proxy Error`。程序会自动重试三次；如果仍然失败，
应稍后再试，不要把这种错误误认为“该位置没有数据”。

### IRSA 结果如何匹配已经下载的 FITS

IRSA 结果的 `cloud_access` 字段包含：

```text
bucket = nasa-irsa-spherex
key    = qr2/level2/.../某个文件.fits
```

本地数据库和 `data/` 目录也使用同一条 S3 key。因此可靠的匹配方式是：

```text
IRSA 返回的 (bucket, key)
            ∩
downloads 表中 status=completed 的 (bucket, key)
            ↓
已经下载且覆盖目标点的 FITS
```

本地文件路径通常就是：

```text
data/<IRSA 返回的 key>
```

不要只按文件名、`observation_id` 或 detector 判断“已经下载”。相同观测可能
存在不同 pipeline version 或重新处理版本；只有完整 S3 key 相同才是同一个
远程对象。

当前 `search` 命令只打印结果，还没有自动执行上述数据库交集，也没有自动生成
下载 manifest。这是下一步可增加的功能，不要把 `search` 当成下载命令。

### 查看当前下载状态

```bash
python -m spherex_pipeline status
```

当前应显示：

```text
completed  10 files  683.16 MiB
```

### 只预览，不下载

```bash
python -m spherex_pipeline download --dry-run
```

它会告诉你：

- 哪些文件需要下载；
- 哪些文件已经存在，会跳过；
- 总共要传输多少数据。

在任何较大下载前，都建议先运行这一步。

### 执行下载

```bash
python -m spherex_pipeline download
```

当前 10 个文件都已经完成，所以再次运行时应该全部跳过，不会重复下载。

### 再次检查 10 个 FITS

```bash
python -m spherex_pipeline verify
```

### 更新测试范围的 AWS catalog

```bash
python -m spherex_pipeline catalog update \
  --prefix qr2/level2/2025W17_4B/
```

这一步只获取文件元数据，不下载 FITS。

### 重新生成 10 文件清单

只有明确希望换一批测试文件时才运行：

```bash
python -m spherex_pipeline select --overwrite
```

平常 debug 不需要反复运行它。

## FITS header 探索得到的结论

桌面独立实验目录：

```text
C:\Users\26823\Desktop\SPHEREx_FITS_exploration
```

其中复制了一份 D2 Level 2B FITS 进行只读研究，没有改动项目里的原始数据。

该样本是一个含 7 个 HDU 的 Multi-Extension FITS：

```text
PRIMARY / IMAGE / FLAGS / VARIANCE / ZODI / PSF / WCS-WAVE
```

与天空覆盖有关的二维天球 WCS 位于第 1 个 `IMAGE` 扩展，不在 PRIMARY。
IMAGE header 包含：

```text
RA---TAN-SIP / DEC--TAN-SIP
ICRS
三阶 SIP 畸变参数
2040 × 2040 图像尺寸
```

实验已经证明，仅使用 IMAGE header 就可以：

1. 计算图像中心和四个角的 RA/Dec；
2. 把目标 `(RA, Dec)` 转换为像素 `(x, y)`；
3. 根据像素是否位于图像边界内判断覆盖；
4. 完全不读取 IMAGE 像素值。

对该样本，PRIMARY 和 IMAGE header 一共只占文件开头 23,040 bytes，约为
完整 68.3 MiB FITS 的 0.032%。因此，如果以后需要自建本地 WCS index，技术上
可以考虑用 S3/HTTP Range Request 只读取 FITS 开头的 header blocks。

`23,040 bytes` 只是这一个 D2、特定 pipeline version 样本的结果，不能写死到
正式程序中。批量实现时必须按 FITS 的 2,880-byte blocks 动态寻找 `END` card，
并抽查不同 detector、planning period 和 pipeline version。

### Gregory 的半对角线建议如何使用

样本图像边长约为 3.48°，所以：

```text
边长 × sqrt(2) / 2 ≈ 2.46°
```

实际四个角距图像中心约为 2.445°–2.477°。因此中心距离适合用来快速排除
明显不相关的 images，但它对应正方形的外接圆，不能作为最终判断。最终判断
应使用完整 TAN-SIP WCS，把 world coordinates 转为 pixel coordinates。

Header 只能回答几何覆盖，不能判断目标像素的 FLAGS、flux、variance、背景或
数据质量；这些仍需读取相应 FITS 扩展。

## 当前阶段的推荐做法

当前优先级已经从“继续扩大随机测试下载”转向 Gregory 提出的 single-point
科学目标筛选。推荐顺序是：

1. 确定一个实际研究目标的 ICRS `RA, Dec`；
2. 运行 `search`，检查 IRSA 返回的 images、detectors、S3 keys 和总容量；
3. 用完整 S3 key 判断哪些结果已经存在于本地；
4. 任选一个返回结果，用 FITS IMAGE header/WCS 独立验证 IRSA 的覆盖判断；
5. 确认结果正确后，再实现明确的 `search → manifest → dry-run → download`；
6. 只有在 IRSA 稳定性、可重复性或离线使用确实成为问题时，才批量研究
   Range Request 和本地 header/WCS index。

现有 10 文件仍应保留作为下载和 FITS 验证的回归测试集，但暂时没有必要仅为
扩大数量而下载 100 或 1000 个随机文件。

## 以后如何扩大文件数量

扩大规模时，建议逐级进行，不要直接从 10 个跳到全部数据：

```text
10 个 -> 100 个 -> 1000 个 -> 一个 planning period -> 多个 period -> 全部数据
```

### 情况一：仍使用 `2025W17_4B`，从 10 个增加到 100 个

先建立一个新的 manifest，保留原来的 10 文件测试清单：

```bash
python -m spherex_pipeline select \
  --limit 100 \
  --manifest catalogs/test100_manifest.csv
```

先检查预计下载量：

```bash
python -m spherex_pipeline download \
  --manifest catalogs/test100_manifest.csv \
  --dry-run
```

确认磁盘空间和传输量后再下载：

```bash
python -m spherex_pipeline download \
  --manifest catalogs/test100_manifest.csv
```

不要使用 `--overwrite` 覆盖 `test10_manifest.csv`，这样原来的 10 文件回归测试可以一直保留。

按照当前文件约 68.32 MiB 的大小粗略估算：

- 100 个约 6.7 GiB；
- 1000 个约 66.7 GiB。

实际运行前仍应以 `--dry-run` 给出的总量为准。

### 情况二：测试另一个 planning period

假设要测试 `2025W18_1A`，先只扫描这个 period 的元数据：

```bash
python -m spherex_pipeline catalog update \
  --prefix qr2/level2/2025W18_1A/
```

然后建立独立 manifest：

```bash
python -m spherex_pipeline select \
  --planning-period 2025W18_1A \
  --limit 100 \
  --manifest catalogs/2025W18_1A_100_manifest.csv
```

再执行 dry-run 和下载。

上面的 planning period 只是命令格式示例。实际使用前应先从 AWS catalog 确认该 period 确实存在，不应猜测目录名。

### 情况三：扫描全部 QR2 Level 2 元数据

运行：

```bash
python -m spherex_pipeline catalog update
```

`config.toml` 中的默认 prefix 是：

```text
qr2/level2/
```

因此这个命令会列出该 prefix 下的全部对象并更新 SQLite，但不会下载 FITS。完成后先导出 catalog：

```bash
python -m spherex_pipeline catalog export
```

然后检查总文件数和总容量，再决定下载范围。

### 情况四：将来需要下载全部数据

当前版本故意要求 `select` 提供一个整数 `limit`，而且一次只方便筛选一个 planning period。它还没有开放“一条命令选择全部数据”的功能。这是为了防止测试阶段意外开始数百 GiB 或更大的下载。

真正准备下载全部数据时，不建议把 `limit` 随意写成一个极大的数字。应先给程序增加一个明确的 `select --all` 模式，并至少执行以下保护：

1. 完成整个 `qr2/level2/` catalog 扫描；
2. 统计对象数和总字节数；
3. 检查本地或 HPC 可用空间；
4. 生成单独的全量 manifest；
5. 将 manifest 分批，例如每批 500 或 1000 个文件；
6. dry-run 后要求明确确认；
7. 下载过程中允许按批次恢复；
8. 在 HPC 上限制同时写入 catalog 的进程数量。

因此，当前扩大到 100 或 1000 个文件不需要修改程序；真正的“全量下载”阶段建议先扩展程序，而不是直接修改配置硬跑。
